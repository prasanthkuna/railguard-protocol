# The 10/10 standard

A project is not 10/10 because the code is sophisticated.

It becomes 10/10 when five independent people can verify five different things:

```text
Engineer       → the implementation is correct
Security lead  → failure boundaries are defensible
Developer      → integration is easy
Enterprise     → operation is safe
Hiring manager → your contribution is obvious
```

Your existing implementation already proves the hardest internal part:

* post-broadcast failures keep authorization frozen;
* reconciliation commits or releases from settlement truth;
* transfer verification checks chain, token, sender, recipient and amount;
* six adversarial failure profiles exist;
* JSON, JUnit and SARIF outputs already run in CI.

What remains is turning **self-proven engineering into externally proven infrastructure**.

# Category 1: Core payment correctness — 10/10

## Current level: approximately 9/10

The important lifecycle bug is fixed, but 10/10 requires proving correctness under infrastructure failure, not just business-logic tests.

## Required invariants

Write these as explicit system invariants:

```text
INV-001
A payment with a transaction hash may never release its reservation
until settlement is definitively reverted.

INV-002
A confirmed payment must match the expected chain, token,
sender, recipient and amount.

INV-003
The same business payment intent may produce at most one
financially effective settlement.

INV-004
A process crash may delay convergence but may not change
the eventual financial outcome.

INV-005
Reconciliation may be repeated indefinitely without
double-committing or double-releasing.

INV-006
Changing material payment facts invalidates all prior approvals.

INV-007
Unavailable policy or state infrastructure fails closed.

INV-008
Off-chain policy bypass cannot exceed on-chain session limits.
```

## Tests required

Add fault-injection tests at every state boundary:

```text
AUTHORIZED → RESERVED
RESERVED → EXECUTING
EXECUTING → SUBMITTED
SUBMITTED → CONFIRMED
SUBMITTED → UNKNOWN
UNKNOWN → CONFIRMED
UNKNOWN → REVERTED
```

For every boundary:

1. Kill the process before the database write.
2. Kill the process after the database write.
3. Repeat the request with the same idempotency key.
4. Repeat it with a different idempotency key.
5. Run two reconcilers concurrently.
6. Run reconciliation repeatedly after completion.

## Database-level protections

Do not rely only on application code.

Add:

```text
Unique constraint:
organization_id + execution_idempotency_key

Unique constraint:
organization_id + guard_authorization_id

Conditional update:
only RESERVED/SUBMITTED/UNKNOWN can transition

Check constraints:
tx_hash required for SUBMITTED/UNKNOWN/CONFIRMED
confirmed_at required for CONFIRMED
released authorization cannot become committed
committed authorization cannot become released
```

Use row locking, serializable transactions or a carefully designed outbox where cross-table convergence matters.

## Chain-specific hardening

Add:

* configurable confirmation depth;
* chain-ID verification;
* RPC-provider disagreement handling;
* removed-log/reorg detection;
* cursor rewind;
* stale pending transaction handling;
* replacement transaction handling;
* RPC timeout classification;
* independent RPC fallback for reconciliation.

## 10/10 exit gate

Core correctness reaches 10/10 when:

```text
□ All invariants are documented
□ All state transitions have fault-injection tests
□ Reconciler concurrency is tested
□ Process restart loses no correlation
□ Reorg or removed-log behavior is tested
□ Database constraints reject impossible states
□ One independent engineer reviews the state machine
□ No critical/high findings remain
```

# Category 2: Failure Lab quality — 10/10

## Current level: approximately 8/10

The lab is real and coherent. It already has APF-001 through APF-006 and machine-readable outputs.

The missing leap is turning it from a repository that tests itself into infrastructure that tests other repositories.

## Build a reusable GitHub Action

The target experience:

```yaml
name: Payment Safety

on:
  pull_request:

jobs:
  adversarial-payment-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: prasanthkuna/agent-payment-failure-lab@v1
        with:
          profiles: "APF-001,APF-002,APF-003"
          target-command: "docker compose up -d"
          target-url: "http://localhost:8080"
          config: ".apf/config.yaml"
          output: "json,junit,sarif"
```

## Define a stable adapter contract

```typescript
interface PaymentFailureAdapter {
  createIntent(input: PaymentIntentInput): Promise<IntentReference>;
  authorize(intent: IntentReference): Promise<AuthorizationReference>;
  execute(
    authorization: AuthorizationReference,
  ): Promise<ExecutionReference>;
  readPaymentState(intentId: string): Promise<PaymentState>;
  readAuthorizationState(
    authorizationId: string,
  ): Promise<AuthorizationState>;
  reconcile(intentId: string): Promise<ReconciliationResult>;
  injectFault(fault: FaultPoint): Promise<void>;
  collectEvidence(intentId: string): Promise<EvidenceBundle>;
}
```

Then implement adapters separately:

```text
x402
CDP
generic REST
smart account
Stellar
GNU Taler later
```

## Version the profiles

Every profile needs:

```text
Profile ID

```

Example:

```yaml
id: APF-003

  - durable payment intent

  payment_status: UNKNOWN

    authorization_status: COMMITTED
```
